## Section 8: Observations and Recommendations

### What worked well

- The run manifest made the campaign reproducible and matched the invocation without discrepancies.
- Strict serial ordering preserved the dependency between the Fibonacci foundation and factorial/dispatch extension.
- HEAD-bound CCRA polling prevented stale reviews from satisfying later review gates.
- Repository-owned validation remained authoritative throughout: 8 tests passed before review fixes, 11 after the first PR's fixes, and 18 for the combined second task.
- Final gates checked CI, review identity, HEAD stability, unresolved threads, base branch, mergeability, issue closure, and cleanup.
- The first PR's two findings were resolved in focused commits; the second PR then converged immediately.

### What could be improved

- Phase 2 for [#2](https://github.com/edburns/dd-3070093-simple-math-linux-x64-01/issues/2) consumed 1,055,157 input tokens, nearly half of all local input tokens. Repeatedly loading the full review procedure and large GitHub responses increased context cost for a two-file change.
- The readiness phase used ad hoc shell probes that produced two avoidable command failures. Although non-gating, they add noise and weaken machine parsing of failure signatures.
- File inspection assumed a `tests/` directory before using repository discovery.
- The 6m 04s between recorded sessions is material for a 34m 41s campaign and is not categorized by the current manifest.

### Recommendations

1. Add reusable script helpers for exact-HEAD checks, bot comment retrieval, and `gh` capability detection so quoting and incompatible flag combinations are tested once rather than rebuilt in each session.
2. Discover changed files from the PR before local reads and use those paths directly; do not assume conventional test directories.
3. Emit a compact structured stage outcome containing review IDs, comments per round, fix commit SHAs, test counts, merge timestamps, and token totals. This would eliminate post-mortem parsing of large Markdown transcripts.
4. Record transition timestamps in the orchestration manifest so launch latency, dependency wait, post-merge cleanup, and post-mortem startup can be separated from agent work.
5. Reduce phase-2 context by loading review instructions once and querying only current-HEAD reviews/comments. This run's high cache-read ratio shows caching helped, but the absolute input-token volume remained large.
6. Preserve the control treatment: do not write inferred lessons to `campaign-lessons.md` when `lessonPropagation` is `off`. Use this run's metrics as a baseline for a matched lesson-enabled campaign instead.
